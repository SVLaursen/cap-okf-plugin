# @gavdi/cap-mcp × cap-okf: their answer on `mcp:resources`

Received from the `@gavdi/cap-mcp` maintainers on 2026-11-17 and recorded here by cap-okf, as
"the contract as built". Their record is their ADR 0013 (`docs/adr/0013-resources-from-code.md`
in that repository), **accepted** (confirmed in their second message of 2026-11-17, whose
contract table is identical to the one below). cap-okf's side is ADR-0010, updated to match on
2026-11-17.

## TL;DR

Yes, they are adding `mcp:resources`, with `register` **and** `registerTemplate` in the same
release, `contractVersion: 1`. Most of the proposal stands. The main difference: **use the
template for concepts, always**. Fixed resources are for a few entry points, such as `index.md`.

## Differences from the proposal

| # | cap-okf proposed | What they build | Why |
| --- | --- | --- | --- |
| 1 | `registerTemplate?` optional, may ship later | Ships with `register`. Feature-detect anyway | Templates are how concepts are served (see 2) |
| 2 | One fixed resource per concept for bundles of 50 concepts or fewer | One template `okf://<ns>/{+path}` for every bundle size, plus fixed resources for `index.md` (and an overview, if added) | Every request builds its own server, so each fixed resource, and its `visible`, costs something on every call, `tools/call` included. A template costs the same for 10 concepts or 10,000 |
| 3 | `visible` returns `boolean \| Promise<boolean>` | `boolean` only | It runs while each request's server is built; an async check would delay every call. Per-concept authorization belongs in the template's `read`, which may be async |
| 4 | `uri` must be absolute | Absolute **and canonical**: `new URL(uri).href === uri`, or `register` throws | The SDK reads fixed resources by `new URL(uri).toString()`. A URI that `URL` rewrites is listed but can never be read. Encode paths from file names (spaces, `%`) before registering |
| 5 | Duplicate `uri` or `uriTemplate` throws | Also a duplicate template `name` | The SDK keys templates by name. A template named like one of their `cap://` templates in a tenant's model is skipped for that request and logged, so choose names like `okf-<ns>-concepts` |
| 6 | 404 from `read` becomes resource-not-found | Same, with the URI only: the error's message is not passed on | The message is written for the developer, not for agents |
| 7 | (not covered) | A `visible` that throws hides the resource for that request and is logged; a `list` that throws adds nothing; a `complete` that throws offers nothing. Completion returns at most 100 values, with `hasMore` | One misbehaving callback should not break `resources/list` or completion for everyone |
| 8 | (not covered) | Template `params` are strings. A hidden fixed URI that a template also matches is answered by the template's `read` | `read` must return 404 for anything the caller may not see |
| 9 | (not covered) | `uriTemplate` is parsed with the SDK's `UriTemplate` and must be canonical once expanded (lower-case scheme and host, encoded spaces), or `registerTemplate` throws | A bad template used to break every request; a non-canonical one never matched |
| 10 | (not covered) | `params` arrive exactly as sent, **still percent-encoded**. Overlapping templates match in sorted `uriTemplate` order | Decode and check `params.path` before reading a file with it (path traversal) |
| 11 | (not covered) | `read` must return a string; anything else is an internal error. `list` must return an array; entries need a string `uri` and `name` outside `cap:`/`ui:`, and only `uri`, `name`, `title`, `description` are passed on (they inherit the template's MIME type) | A malformed callback result is contained instead of breaking the list |
| 12 | (not covered) | `complete` is called only for the template's own variable names | Other argument names get no values |
| 13 | (not covered) | A listener must register before any `await`; a registration that throws fails startup with a `cap-mcp:` message | The registry closes when the emit returns |
| 14 | (not covered) | The types (`ResourceRegistry`, `FixedResource`, `TemplateResource`, `ResourceContext`, `ListedResource`) are exported from `@gavdi/cap-mcp` as types only | For a contract test; importing types adds no runtime dependency |

Everything else is as proposed: emitted once on `served` after `mcp:apps`, also when nothing else
produces resources; synchronous registration, closed afterwards; `cap:` and `ui:` reserved;
callbacks inside `cds.context` (user, tenant, locale) and not in `srv.tx`; no caching across
requests; the `resources` capability only when the caller has a resource, with
`listChanged: false`; hidden and unknown URIs answer the same; both protocol eras.

## Answers to cap-okf's questions

1. **Will they add `mcp:resources`?** Yes, as in their ADR 0013, with the differences above.
2. **`registerTemplate` together or later?** Together.
3. **Unbound functions as tools, with doc comments as descriptions?** Yes: `@mcp` on
   `OkfService` exposes its functions as `OkfService_getConcept` and `OkfService_searchConcepts`,
   and the `Index` entity as `OkfService_Index_query` and `OkfService_Index_get`, with no change on
   their side. The description comes from `@mcp.description`, then `@description`, then the doc
   comment. Doc comments reach the model only when the app sets `cds.env.cdsc.docs = true` (their
   ADR 0011: the app's choice; they never set it). Write `@description` on the service, entity,
   functions and parameters so the descriptions arrive with either MCP plugin, whatever the app's
   setting.
4. **Is async `visible` expensive?** Yes, which is why it is synchronous: it would run before
   every request is answered.

## One more thing for cap-okf

Don't decide the fallback "by the end of `served`": they emit from their own `served` listener,
and if cap-okf's runs first it would fall back although they are about to emit. Check after
`served` has finished, e.g. in a `listening` listener, or remember that the event arrived and
decide there. (ADR-0010 already does this.)

## What happens next (their side)

1. Built test first, with demo targets in their bookshop app (fixed `notes://bookshop/…`
   resources and a `notes://bookshop/topics/{+path}` template). Rows 9–14 came out of building and
   reviewing it. Their tests include a `read` that calls a CAP service as the caller, so
   `@restrict` applies to what is read through `cds.context`.
2. Their ADR 0013 is accepted.
3. Contract changes after that go through both ADRs. `contractVersion` rises only for breaking
   changes.
