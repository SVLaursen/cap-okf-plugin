# cap-okf — Implementation Plan

Work top to bottom. Each task lists **Depends on**, **Test first** (the failing tests you write before code) and **Done when**. A phase ends at a gate; after the gate check, stop and wait for human sign-off before starting the next phase.

Legend: `[ ]` open · `[x]` done (tick it in the same PR that completes the task).

## Target layout


## Phase 2 — CDS exporter → Gate G3

- [x] **2.1 Mapper registry + entity mapper.** Path from fully qualified name (`model/<ns as folders>/<Name>.md`), `type: Entity`, title, description, `resource: cds:<fqn>`, tags. Body: keys, elements with types, associations/compositions as links. Maintainer decisions 2026-11-16: an elements table plus a list of association links; tags `[cds, <kind>, <namespace>]`; description from `@description`, else the doc comment's first sentence; links in the absolute `/model/…` form.
- [x] **2.2 Service and projection mappers.** Service body lists exposed entities, actions and functions as links. Projections link to their source. Maintainer decision 2026-11-16 (revised the same day): projections are written as `type: Projection` and views as `type: View`, not as `type: Entity`, because they aren't stored entities; the service still lists them under Entities.
- [x] **2.3 Action, function, type, aspect, event mappers.** Parameters and return types; bound actions listed on their entity. Maintainer decisions 2026-11-16: a bound action gets an `### name` subsection on its entity in the same layout as an unbound action's concept; a type defined in the model is a link to its concept wherever a type is shown.
- [x] **2.4 Authorization section (ADR-0003).** Render `@restrict` and `@requires` into a section wrapped in `<!-- okf:auth:start -->` / `<!-- okf:auth:end -->` under `## Authorization`. Nothing about authorization appears outside it.
  - Test first: AdminService fixture renders the section; a grep test asserts no `@restrict` content outside the markers.
  - Maintainer decisions 2026-11-16: `@readonly`, `@insertonly` and `@Capabilities` count as authorization and go inside the section; a member of a service repeats the service's rules there, as inherited.
- [x] **2.5 i18n.** Resolve `{i18n>key}` titles and descriptions in the default language; fall back to the key name.
- [x] **2.6 Include/exclude.** `include: "services"` (default) exports only definitions reachable from services; `"all"` exports everything; `@okf: false` excludes; `@okf.tags` adds tags.
  - Maintainer decisions 2026-11-16: "reachable" means the services, their members and everything their concepts refer to (sources, association targets, element, parameter and return types), transitively. A concept never mentions a definition that isn't exported, as cap-mcp v2 and CAP do: associations and other references to it are left out, not written as names. `@okf: false` works on definitions, elements, parameters and bound actions.
  - Maintainer decisions after review: `@okf: false` follows CAP's annotation copying (an aspect's reaches the entities including it, a source's its projections; `@okf: true` opts back in); an element, parameter or return value of an excluded *type* stays, shown with its built-in type; a definition under one that isn't exported (a service member, `X.texts`) is left out. One exception to "never mention": an auth-section where-condition is shown as CAP applies it, even if it names a hidden association path (ADR-0003 strips the section for unauthenticated readers).
- [x] **2.7 Exporter.** Orchestrates mappers, generates `index.md` files, injects `{ now, version }` into `generated`.
  - Note from 2.6: pass inferred CSN as `cds.load` returns it (CSN compiled for a runtime adds foreign keys and draft tables that name hidden associations), and always pass `selectExported(model, include)` as the context's `isExported`; its default lets everything through.
  - Note from 2.5: build the text lookup with `defaultLanguageTexts(cds, model)` from the model as `cds.load` returns it (it needs `$sources`). A model compiled from a string has `$sources: ['<stdin>.cds']`, so its `_i18n` folder is looked up relative to the working directory.
  - Test first: two runs with the same inputs produce byte-identical output.
- [x] **2.8 `cds compile --to okf`.** Prints the bundle tree and, with `-o <dir>`, writes it. Maintainer decisions 2026-11-17: without `-o` it prints one path per line; the clock is `SOURCE_DATE_EPOCH` when set, else the current time.
- [x] **2.9 `cds build` task.** Writes `gen/okf` and, for staging builds with a `nodejs` task, the same files to `<nodejs dest>/okf-bundle/` (ADR-0007); runs validation; fails only on errors. In-place builds (`build.target: "."`) never touch `okf/`. Decisions (defaults, open to the maintainer): the bundle always goes to `<build target>/okf` (in place: `<root>/gen/okf`), whatever `src`, `dest` or `--dest` say; the task loads the build's default model paths without the project root itself, as the base model (no feature toggles), with doc comments (`options()` adds `docs: true`); both output folders are emptied before writing; same clock, version and `cds.okf.include` as 2.8; on validation errors `gen/okf` is still written for review, but nothing goes into the deployed app; warnings are logged after the build.
  - Test first: `cds build` of a fixture app writes `gen/okf` and `gen/srv/okf-bundle/`; an in-place build leaves `okf/` untouched.
- [x] **ADR-0004 revisit (maintainer note, 2026-11-17).** The change was ADR-0006 revision 2 (plus an amendment note for ADR-0004). Done 2026-11-17: drafted as ADR-0010 (Proposed, supersedes ADR-0006, since Accepted ADRs can't be edited), merged with the task 0.5 findings; Phase 4 tasks 4.1 and 4.4–4.8 updated below. Nothing in 2.10 changes: ADR-0010 keeps the bundle hash out of `index.md` (OKF §8 allows only `okf_version` there).
- [x] **2.10 Golden tests.** Commit `test/golden/bookshop/`; diff on every run. Fixed inputs (`now` 2026-01-01T00:00:00Z, version `0.0.0-golden`), so neither the clock nor a release changes them; `npm run test:update-golden` rewrites the whole folder; the golden bundle also validates without findings.

**Gate G3:** golden bundle matches; determinism test green; `@okf: false` and the auth section tested.

## Phase 3 — Curation and developer experience → Gate G4 → release 0.1

- [x] **3.1 Merge.** Merge curated `okf/` with generated `model/`; a curated file under `model/` is an error with a fix hint. Decisions (defaults, open to the maintainer): `cds compile --to okf` merges `<cds.root>/okf` too, so `-o` gives what `cds build` gives; a curated folder that holds a listed concept (a Markdown file other than `index.md`/`log.md`) below it and has no `index.md` of its own gets a generated one; other folders get none and aren't listed (known limit: a top-level curated folder whose only Markdown file is its own `index.md` isn't listed in a generated root index); cap-okf layout rules L1 (error, the file is left out: a curated file in `model/`; a path that is the same file or folder as another, letter case and Unicode form aside, or a file where a folder is; `INDEX.md`/`Log.md` and other spellings of OKF's reserved names) and L2 (warning: a curated root `index.md` that doesn't link to `model/`); messages name `okf/<path>` for curated files; non-Markdown curated files are copied byte for byte by `cds build`, while `cds compile -o` writes them only when they are UTF-8 text (CAP's writer takes strings; a BOM is kept) and notes the rest; `okf` as a file is an `[okf]` setup error.
- [x] **3.2 Messages.** `[okf] <file>:<line> — <what>.` + indented fix. Errors fail the build; warnings never do. Maintainer decision 2026-11-17: model clashes only. Validator and merge findings already had file, line, rule and fix (2.9, 3.1); two definitions whose concepts clash now name the `.cds` file and line of both (from `$location`, relative to the project root), rule M1 and the fix, and print without a stack trace in `cds build` and `cds compile`. Setup errors (config values) keep their `[okf] <setting> — …` message and fix, without file, line or rule: CAP doesn't say which config file a value came from.
- [x] **3.3 `cds add okf`.** Creates `okf/index.md`, one example concept, `.gitignore` entry for `gen/okf`, a commented `cds.okf` block. Idempotent. Maintainer decision 2026-11-17: JSON has no comments, so `cds.okf` is written to `package.json` with its default values (`include: "services"`, `serve: { static: false, mcp: false }`); the README (3.5) explains them. Decisions (defaults): nothing the developer set is changed: `cds.okf` is added only when no CAP config file mentions `okf` in any profile (CAP reads `package.json` last, so a new block would override `.cdsrc.*`); `okf/index.md` and the example go only into a missing or empty `okf/`; `.gitignore` gets `<build target>/okf` only when no line (a negation too) decides about it; an app's own `build.tasks` lists get `{ "for": "okf" }` (ADR-0005 (b)) in `package.json` and `.cdsrc.json`, with a note for `.cdsrc.yaml`/`.cdsrc.js`; files keep indentation, line endings and final newline; `--for <profile>` gets a note (the defaults are the same in every profile); a missing or invalid `package.json` is an `[okf]` error and nothing is written.
- [x] **3.5 README.** Quick start, config reference, annotation reference, examples. Written for a CAP developer who has never heard of OKF. Written with what 0.1 does; serving (`serve.static`, `serve.mcp`) is marked as planned for 0.2. Covers the README duties from ADR-0003 (auth sections on disk, `gen/srv`), ADR-0005 (own `build.tasks`, static route shown in the README once 4.3 exists) and ADR-0007; the `@cap-js/mcp` autowire note (ADR-0006/0010) is added with 4.7.
- [x] **3.6 Pilot harness.** `test/pilot/`: a question-set format and a script that scores a CAP agent's answers with and without the bundle. The human supplies the domain and questions. Maintainer decision 2026-11-17: answers in files, nothing calls a model (no API key, no new dependency). `questions.yaml` (domain; questions with `expect` facts, alternatives allowed, and optional `avoid` claims) and `answers/<run>.yaml` (agent, `bundle: true|false`, answers by id); `npm run pilot:score -- test/pilot/<set>` prints a Markdown report (summary per run, every answer with what it misses); the counts guide, the human judges. `test/pilot/example/` shows the format on the bookshop fixture with hand-written answers.

**Gate G4:** pilot shows improvement (human judges); every message has file, line, rule and fix; README reviewed. Human cuts release 0.1.

- [x] **4.2 Auth filter.** `filter.ts` removes marked sections; pure, unit tested. `src/core/filter.ts`: `forReader(text, { isAuthenticated })` and `withoutAuthSections(text)`. Decisions (defaults, fail closed where the 2.4 contract is silent; reviewed): every section goes, wherever it is (curated files may have several); sections nest; a start marker without an end removes the rest of the file; an end marker without a start withholds everything before it; a whole line counts as a marker in any case or inner spacing, with spaces, invisible format characters or a quote (`> `) around it; markers count inside code blocks too; `\n`, `\r\n` and a lone `\r` end lines; the marker constants live in `src/core/filter.ts` and the generator imports them; the blank lines just before a section go with it; line endings and the final newline are kept.
  - Contract from 2.4: a marker counts only as a whole line (`<!-- okf:auth:start -->` / `<!-- okf:auth:end -->` alone on a line), and a generated concept has at most one section, at the end of its body. Text elsewhere can contain marker-like text (e.g. a title), which must not cut anything.
- [x] **4.3 Static route (Node).** `cds.okf.serve.static: false | true | "/path"`, `text/markdown; charset=utf-8`, uses CAP's auth middleware to decide authentication. Not listed on the CAP index page (ADR-0005). `src/serve/static-config.ts`, `source.ts`, `static-route.ts`. Decisions (defaults): the setting is read at bootstrap, so a bad value stops a server but never `cds build`; routes are `/` plus segments of letters, digits, `-`, `_`, `.`; `/okf` redirects to `okf/` (relative, 302); folder paths serve their `index.md`; files that aren't UTF-8 text get 404; one bundle per server; a setup error while generating stops startup (curated errors don't); no CORS; GET and HEAD only (405 with `Allow`); `Cache-Control: private, no-cache` and `Vary: Authorization, Cookie`; non-Markdown files as `text/plain; charset=utf-8`; paths are decoded once and must be bundle paths (404 otherwise); in development the bundle is generated once at `served`, with curated errors left out and logged, and a warning under `NODE_ENV=production`.
- [x] **4.3a `cds watch` (moved from 3.4, maintainer decision 2026-11-17: it needs serving).** Serving under `cds watch` uses the in-memory bundle, which follows model changes because the server restarts (ADR-0007). Optional: regenerate `gen/okf` for inspection on change (debounced); no file writes outside `gen/okf`. Done 2026-11-17 (maintainer decision: document `--ext md`): the in-memory bundle already follows a restart (4.3); `cds watch` doesn't restart on Markdown and a plugin can't change its file types, so the README shows `cds watch --ext …,md` and the demo's `watch` script uses it. Decisions (defaults): `as` may be one string; unknown `as` values are left out with a warning, and with none left the plugin's natural channel is used; `requires` is a role or a list of roles (one is enough, as with `@requires`); an unknown `plugin` name and a value that isn't false, true or an object are setup errors. `namespace: null` derives it (so a profile can reset it); a set namespace that isn't valid text is an error, and an invalid derived one names the package.json name.
