## What Phase 4 delivered

- **Static route** `cds.okf.serve.static`.
  - It serves the built bundle in production and an in-memory one in development.
  - It decides authentication through CAP's own middleware, with private caching and GET/HEAD
    only.
  - It isn't on the CAP index page.
- **MCP over `@gavdi/cap-mcp` v2** (`cds.okf.serve.mcp`), with a shared `namespace` and
  `requires`. It has two channels:
  - **Resources** (`okf://<namespace>/index.md` and one template for every concept, through
    `mcp:resources`);
  - **Tools** (a read-only, index-first `OkfService`: `Index`, `getConcept`, `searchConcepts`,
    `bundleInfo`, with no OData endpoint).
- **ADR-0003 filter** (`src/core/filter.ts`), shared by every channel.
- **Contract suite** (`test/contract/`), run on every channel, by hand-written JSON-RPC and by
  the official MCP client against a fixture app.
- **Config validation**: unknown keys under `cds.okf` are warned about, and `cds build` checks the
  serve settings early.
- **Decisions recorded along the way:**
  - ADR-0010 (MCP contracts, rev. 2) and ADR-0011 (the `Index` query subset), both Accepted.
  - Two behaviours accepted as they are on the tools channel: 401/403 instead of 404 for callers
    who don't meet `requires`, and the unfiltered `bundleHash`.
  - `@cap-js/mcp` parked; Java out of the first release.

## Open issues and risks carried forward

1. **`@cap-js/mcp` (4.7) is not supported.** The gate criterion stays unmet until it comes back.
   Its fixture app (the second half of 4.8) and the missing-resource-hook warning for
   `as: ["resources"]` come with it. Today that setting is quietly ignored.
2. **The `@gavdi/cap-mcp` integration rests on an unreleased build** (`2.0.0-alpha.0`).
   - When the plugin is released: rerun the contract suite against the published package.
   - Decide whether it becomes a dev dependency (GOVERNANCE: a PR note).
   - Switch the `integrations` job to it.
   - Contract changes go through both ADRs (theirs 0013, ours 0010).
3. **Badly marked curated files** (spec-checker finding; already a follow-up in the progress log
   since 4.2).
   - The filter fails closed, so no authorization text leaks. But an end marker with no start
     removes everything before it, frontmatter included, so an anonymous reader gets a file
     without frontmatter (breaks OKF §11(1) for that reader).
   - An unclosed start marker inside a code fence cuts off the rest of the file.
   - `cds build` reports neither today.
   - **Proposed:** a build-time `[okf]` finding for unpaired, nested or near-miss markers in
     curated files.
4. **No CI has run yet.** There is no remote. The `integrations` job also needs the
   repository variables above.
5. **The pilot is still parked** (G4). Phase 4 doesn't change that.
6. **Smaller items from the progress log:**
   - `.texts` concepts without a description (W1; 6 spec warnings);
   - `@Common.Label` isn't read;
   - the plugin shows a tool error's message twice (`<message>: <message>`), its own formatting;
   - the tools channel answers a caller without the role with "unknown tool", not 404 (accepted).
